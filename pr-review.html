PR Review Cheatsheet · Structured Correctness

Dijkstra-inspired review through desired effects, refinement, invariants, topology, commitments, and evidence.

Examples, agent roles, metrics, and source notes
● stated = issue / spec ● enforced = types / code ● observed = tests / runs ● inferred = reviewer hypothesis

1 Establish the thesis

Name the desired effectWhat must become true for the user/domain?
State the semantic deltaWhat observable behavior changes?
Protect unchanged behaviorWhat must remain exactly as before?
Separate fact from inferenceLabel claims by their strongest evidence.
Write the thesis in one paragraphIf this is impossible, the PR may mix decisions.

2 Map the refinements

effect → domain → workflow → contract → representation → runtime
Ask what the upper layer assumes
Ask what the lower layer guarantees
Name every new assumptionThen locate where it is enforced.
Find representation leakageDo upper layers know incidental storage details?
Test the cutCould the lower implementation be replaced?

3 Build the invariant ledger

Write each predicate preciselyAvoid “should work” or vague correctness claims.
Name its stable pointsEntry, exit, commit, settle, acknowledge.
init Establish it
preserve Keep it on every path
exit Derive the postcondition
settle Prove termination/quiescence

4 Record commitments

Identify the decisionIntroduced, removed, replaced, or postponed?
Find its structural owner
Measure concept spanHow many layers know the concrete choice?
Name excluded alternativesWhich realistic option is now harder?
Run the pearl testOne replaceable decision or scattered edits?
Avoid speculative generalityLocalize necessary choices; do not abstract blindly.

5 Diff the topology

control New states or transitions?
data Stale, lossy, duplicate paths?
deps Cycles, fan-out, blast radius?
trust Validation or auth bypass?
failure Retry, recovery, compensation?
runtime Do deployment assumptions match?

6 Falsify, classify, teach back

Search concrete counterexamplesBoundaries, races, retries, cancellation, failure.
Map tests to obligationsGreen CI is evidence, not proof.
defect Show violated property + path
question State unresolved obligation
Report uninspected scopeCallers, tests, graphs, or runtime paths not checked.
Teach the solution backHow it works, relies, fails, and changes later.
North-star question: What does this PR make true, what assumptions make that possible, where are those assumptions encoded, and how far through the system does each new design commitment reach?  ·  Review in this order: desired effect → semantic delta → commitment delta → refinement ladder → invariant ledger → topology delta → counterexamples → option test → findings → teach-back.  ·  Open the deep dive →
