Deep dive · Dijkstra-inspired PR review

Reviewing PRs as structured correctness arguments

Move beyond line-by-line diff inspection. Reconstruct what the change makes true, how each layer establishes it, which invariants survive execution, and how far each new design commitment reaches.

The five lenses
  • Desired effect
  • Refinement
  • Invariants
  • Topology
  • Commitments
Core thesis. Review a PR as a proposed refinement of a program: every abstraction layer has a contract, every meaningful execution boundary has truths that must hold, and the change must preserve or deliberately revise those truths. The textual diff is evidence; it is not the real object of review.

1. Dijkstra’s foundation

E. W. Dijkstra’s Notes on Structured Programming is about composing understandable programs, but its ideas map naturally onto modern code review.

Respect cognitive limits

Dijkstra begins by treating human intellectual capacity as a hard design constraint. Large programs cannot be understood by mentally simulating all possible executions. Clarity has quantitative aspects: the number and interaction of concepts matter, not merely whether each line is individually readable.

“as a slow-witted human being I have a very small head”

“On our inability to do much,” EWD249

PR implication: size is not just lines changed. Count interacting design decisions, state transitions, assumptions, and architectural boundaries. A small diff can have a large intellectual surface.

Testing is attempted falsification, not proof

Black-box testing samples a negligible subset of possible behavior. Confidence in correctness therefore depends on the internal structure that supports an argument about all relevant computations.

“Program testing can be used to show the presence of bugs, but never to show their absence!”

“On the reliability of mechanisms,” EWD249

PR implication: green CI is evidence, not the conclusion. Map tests to contracts and invariants, then identify the obligations that examples cannot establish alone.

Review the computation, not the text alone

A program exists to evoke computations that establish a desired effect. The reviewer’s task is therefore to connect static text to dynamic behavior: state changes, ordering, retries, errors, concurrency, and externally observable effects.

“My point is that a program is never a goal in itself; the purpose of a program is to evoke computations and the purpose of the computations is to establish a desired effect.”

“On understanding programs,” EWD249

Use the right mental aid

1 Enumeration

Use for a small, bounded sequence of actions or branches. Inspect each relevant case and derive the net effect.

2 Induction

Use for loops, recursion, repeated messages, retries, and state machine cycles: initialize, preserve, exit, and terminate.

3 Abstraction

Reason about a named operation by the properties its contract guarantees, without expanding all lower-level details.

4 Simplicity

When the correctness argument becomes long or clever, treat that as pressure to simplify the structure rather than celebrate cleverness.

Think in pearls, cuts, and program families

Dijkstra describes a program as a necklace of pearls, each embodying an independent design decision. A cut between pearls is an interface: the lower section provides the machine assumed by the upper section. A concept’s range of validity is the set of pearls that know about it.

Overlapping, long-lived concepts create a thicker logical rope—a system that is more tightly interconnected and harder to adapt. A change is safer when it replaces a coherent pearl while preserving the contracts above and below it.

Programs also belong to families of possible variants. Adaptability is not speculative generality; it is the ability to isolate a foreseeable choice so that changing it does not require “brain-made” edits scattered across the system.

2. “True at every stage” has two meanings

An invariant does not need to hold after every source statement. It can hold before and after a compound action while temporarily failing inside that action. The reviewer must name the stable points where the truth is required.

Each lower level must provide the operations and properties assumed by the level immediately above it.

At every cut, ask:

  • What does the upper layer assume?
  • What does the lower layer guarantee?
  • Does that guarantee fully implement the upper contract?
  • What new assumption did the refinement introduce?
  • Where is the assumption enforced?
  • Could the representation be replaced without changing unrelated upper layers?

State may be transiently incomplete inside a protected operation. The review must establish where that state can be observed.

Stable boundaries can be public operation entry and exit, loop entry, transaction commit, message acknowledgement, promise settlement, retry exhaustion, or compensation completion.

3. The three-axis review model

Axis 1 — Refinement: does each “how” implement the “why” above it?

Reconstruct the chain from user or domain effect to runtime mechanism. A PR becomes suspicious when a lower-level choice silently determines upper-level behavior—for example, when a database flag leaks into UI policy without an explicit domain decision.

For each level, record its responsibility, contract, implementation, new assumptions, private state, observable side effects, and replacement boundary.

Axis 2 — Execution: what must remain true?

{ assumptions ∧ preconditions ∧ invariants }
        changed action
{ intended postconditions ∧ preserved invariants }

For every repeated or stateful boundary, check:

  1. Initialization: the invariant is established.
  2. Preservation: every changed path maintains it.
  3. Exit: the invariant plus the exit condition implies the result.
  4. Termination or settlement: the operation cannot repeat or remain pending forever without an explicit policy.

Extend this reasoning to async and distributed systems: retries, cancellation, partial failure, idempotency, transaction scope, stale responses, and externally visible intermediate states.

Axis 3 — Topology: which paths and boundaries changed?

Model the PR as changes to several overlapping graphs rather than one dependency graph. This reveals how behavior, authority, data, and failure can now travel through the system.

4. Add a commitment delta

A textual diff says what text changed. A commitment delta says which design choices became fixed, replaced, postponed, localized, or spread.

For each new commitment, ask:

  1. Why must this decision be made in this PR?
  2. Where is it structurally owned?
  3. Which modules know about it?
  4. Which invariants depend on it?
  5. Which foreseeable alternative does it exclude?
  6. Could it be replaced at one explicit boundary?
  7. Would the surrounding correctness argument remain valid?

Concept span

concept span = number of architectural layers
               that know a concrete decision

A high span is not automatically wrong, but an increase means more code and more reasoning now depend on the choice. Ask whether upper layers know the domain concept—draft—or its incidental representation—status === "DRAFT".

Contract minimality

The upper layer should know only the properties required for its reasoning. Look for leaked storage layout, incidental ordering, internal identifiers, mutable collections, cache details, lifecycle bookkeeping, or unstated side effects.

  • Completeness: does the implementation provide everything the caller requires?
  • Restraint: does the caller rely only on behavior the interface promises?

The counterfactual option test

Try one or two realistic alternatives: another database, a queued implementation, one adjacent domain state, a second provider, or streaming data. The system need not support the alternative now. Ask whether it would replace one pearl or require coordinated edits throughout the repository.

5. Treat topology as a multi-graph

This is a modern extension of Dijkstra’s discussion of disciplined control-flow topology and his “logical rope” metaphor—not a claim that EWD249 defines these exact graphs.

TopologyNodes and edgesPrimary question
Refinement / responsibilityClaims, decisions, components, “implemented by” edgesIs each requirement implemented at the right level and in one clear home?
Control / stateStates, transitions, branches, loopsAre illegal states or transitions newly reachable?
Data / lineageInputs, transformations, caches, stores, outputsWhere can data become stale, lossy, duplicated, or inconsistent?
Dependency / callModules, symbols, services, imports, callsDid the PR introduce cycles, hidden coupling, or excessive fan-out?
Trust / authorityActors, validation points, privileged effectsIs there a new path from untrusted input to a sensitive operation?
Failure / recoveryFailure points, propagation, retries, compensationCan failure cross a boundary without translation or recovery?
Runtime / deploymentProcesses, queues, stores, network linksDo code assumptions match the real execution topology?

Useful topology-diff signals

  • New architectural-boundary crossing.
  • New cycle or strongly connected component.
  • Increased fan-in, fan-out, or reachable blast radius.
  • Bypass around an interface, authorization check, or validation point.
  • Newly reachable side effect or privileged sink.
  • Longer concept span across abstraction layers.
  • Failure path without compensation, recovery, or explicit propagation.

Important: these are risk indicators, not correctness proofs. A new edge may be precisely what the feature requires. The reviewer must connect the signal to a violated obligation or leave it as a question.

6. Produce a structured change argument

Before emitting review comments, the agent should build a compact, auditable model of the change.

# 1. Change thesis
The PR intends to establish ...
It intentionally changes ...
It must leave ... unchanged.

# 2. Evidence and uncertainties
- Stated facts: issue / spec / PR description
- Enforced facts: types / schema / validation / code
- Observed facts: tests / executed behavior
- Inferred hypotheses: reviewer interpretation
- Missing or contradictory information

# 3. Commitment delta
| Decision | Before | After | Scope | Reversible at | Evidence |

# 4. Refinement ladder
| Level | Responsibility | Contract | Implementation | New assumptions |

# 5. Invariant ledger
| ID | Predicate | Stable points | Source | Enforcement | Evidence | Status |

# 6. Topology delta
- Paths added or removed
- Boundaries crossed or bypassed
- Concept spans widened or narrowed
- Blast-radius changes
- New trust, failure, or side-effect paths

# 7. Counterexample search
| Candidate | Expected | Actual / evidence | Result |

# 8. Program-family analysis
- Decision being replaced
- Future variants made easier or harder
- Unrelated layers newly coupled

# 9. Findings
Only evidence-backed defects.
Risks remain questions or proof obligations.

# 10. Teach-back
- The solution works by ...
- It relies on ...
- Its most important invariant is ...
- It fails safely / unsafely when ...
- A future change to X would touch ...

Use an evidence vocabulary

StatedIssue, spec, docs
EnforcedTypes, schema, code
ObservedTests, traces, runs
InferredReviewer hypothesis

The vocabulary prevents an agent from presenting a plausible interpretation as a verified fact. A finding should identify the property, a concrete execution path or counterexample, exact evidence, assumptions, and a focused remediation or test.

7. Divide agent work by reasoning role

Start with three analytical lanes and a synthesizer. Avoid a large undirected swarm: agents should share proof obligations, not vote on conclusions.

1 Refinement reconstructor

  • States the desired effect and semantic delta.
  • Traces the changed call paths and contracts.
  • Builds the refinement ladder.
  • Identifies cuts and new assumptions.

2 Invariant falsifier

  • Extracts candidate invariants.
  • Names stable execution points.
  • Searches boundaries, failures, retries, races, and cancellation.
  • Returns violations, disproved concerns, or open obligations.

3 Topology mapper

  • Builds before/after graph slices.
  • Finds boundary crossings and bypasses.
  • Reports concept-span and blast-radius changes.
  • Does not label structural deltas as defects alone.

4 Synthesizer

  • Reconciles claims by evidence.
  • Runs deterministic checks.
  • Builds the structured argument.
  • Only then proposes review comments.

Let LLMs supply hypotheses and explanations. Let deterministic tools supply diffs, AST/reference graphs, schemas, static-analysis output, tests, and runtime traces where practical.

Rules that keep reviewers honest

  • Every invariant is labeled stated, enforced, observed, or inferred.
  • Every defect identifies a violated obligation and concrete evidence.
  • A plausible concern without a counterexample is a question, not a finding.
  • Missing tests are not automatically defects; name the uncovered obligation.
  • Passing tests do not establish a general property.
  • Agent conflicts become open obligations rather than majority votes.
  • Suppress style comments unless style obscures a contract, invariant, or design decision.
  • Report inspected callers, tests, and unexplored areas.

8. Worked example: “Save draft”

Desired effect

An owner can persist work without publishing it.

Domain invariants

  • Only the owner can mutate the draft.
  • Saving cannot make content publicly visible.
  • A successful response identifies the version actually persisted.
  • Published content cannot silently revert to a stale draft.

Execution invariants

  • Retries do not create duplicate drafts.
  • A failed save does not leave the UI claiming success.
  • Concurrent save and publish operations have a defined outcome.
  • Cancellation does not discard a previously confirmed save.

Questions that reveal the foundation

  • Topology: did the endpoint reuse the authorization cut, or create a direct path from request data to persistence?
  • Adaptability: is “draft” a domain state, or a database flag whose representation leaks through UI, API, analytics, and notifications?
  • Execution: which write wins when save and publish race?
  • Evidence: is ownership only stated in the PR, or enforced by the query and covered by an adversarial test?

9. The smallest worthwhile experiment

  1. Choose one medium-sized PR and review it normally, but do not comment yet.
  2. Have one tool-enabled agent produce the structured change argument.
  3. Compare its model with yours: missing invariants, incorrect assumptions, overlooked execution states, and surprising topology changes.
  4. Measure useful defects, false positives, unsupported claims, time to accurate teach-back, obligations backed by evidence, and predicted versus actual blast radius.
  5. Split into specialized agents only after the single reviewer’s failure modes are visible.

The refined review sequence

1. Desired effect       — What must become true?
2. Semantic delta       — What changes or stays unchanged?
3. Commitment delta     — Which decisions become fixed or postponed?
4. Refinement ladder    — How does each layer establish the one above?
5. Invariant ledger     — What must hold, and at which stable points?
6. Topology delta       — Which important paths and boundaries changed?
7. Counterexamples      — Can a changed path violate an obligation?
8. Option test          — Is each commitment localized and replaceable?
9. Findings             — Satisfied, violated, or unresolved obligations
10. Teach-back          — Can you explain the solution and foundation?
North star:
What does this PR make true, what assumptions make that possible, where are those assumptions encoded, and how far through the system does each new design commitment reach?
